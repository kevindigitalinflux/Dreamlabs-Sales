## Why (Kevin, 2026-11-11)
The platform is meant to let a rep send about 100 emails per day without hand-reviewing every lead. Today it is too manual: after Deep find many leads keep "unverified" suggested emails, many still ask the user to pick a Companies House company, and each lead is reviewed one by one.

## Evidence (Claude, production, read-only, 2026-11-11)
345 leads; only 51 ever assessed (5 ready, 14 almost, 32 needs work); 294 never had a Deep find. Among the 51: `verified_email` missing 40, `confirmed_website` 37, `company_match` 7, `decision_maker` 4. UK leads without a company number: 251 (8 rejected). Cause: SMTP cannot confirm Microsoft 365 / Google-hosted mailboxes (most businesses), so a guessed `first.last@domain` stays "unverified" forever and readiness punishes it. The 2026-11-05 send bounced about 10% (7 bad of 72 recipients), so the sender reputation needs a guard.

## Kevin's decisions (2026-11-11, these are authorisation for the described behaviour only)
1. **Auto-send rule: strong evidence plus well-supported guesses.** The platform may send automatically (inside the existing send window, daily caps, Pause/Stop controls and the pre-send checker) to addresses in tiers T1 and T2 below. T3 goes to a short "needs a look" list.
2. **Company match: auto-pick on AI web proof** at every effort level (Low included). Ask the user only when the evidence conflicts.

## Evidence tiers for a recipient address (one pure module, tested, used everywhere)
- **T1 strong:** checker `valid`; or the address has replied before (`email_outcomes.replied`); or the address was published by the company itself (found on its own site, Places listing, or the lead's own saved email that is not a guess).
- **T2 supported guess:** a generated address whose format is shared by at least two real (T1) addresses of DIFFERENT people at the same domain (the existing "Pattern-supported" rule), domain has a mail server, address not role-only on a hosted/catch-all domain.
- **T3 weak:** any other guess, role address on a hosted/catch-all domain, unverifiable with no supporting pattern.
- **Never sendable:** `bounced_hard`, checker `invalid`, domain has no mail server, syntax invalid, opted out, on the blocklist.

## Items (tests first, one commit each)
1. **Sendability module.** Pure, import-free function `recipientTier(address, evidence)` returning `T1|T2|T3|never` plus a plain reason string, built on the existing `inferDomainPattern` / `formatEvidence`, `email_outcomes` lookup, checker verdicts and `roleAddressNeedsReview`. Single source of truth; list every place that currently decides "verified email" (readiness, Deep find readiness text, picker "Has a verified email" filter, `sendLeadEmail`/`emailPreSend`) and report which ones use it after this item.
2. **Readiness redefinition.** `evaluateReadiness`: a lead is `ready` when it has at least one T1 or T2 recipient and a company name; `confirmed_website`, `decision_maker`, `company_match` become informational (shown, never block `ready`, except `websiteSuspect` / foreign-phone mismatch, which still forces `needs_work`). Keep the stored fields and badges; new missing keys `sendable_email` replaces `verified_email` (keep reading old values). Update the plain reason strings ("Ready to send: 2 supported addresses" / "Almost: no sendable email"). The picker's verified-email filter and the readiness sort use the new rule. Report what changes for the 51 assessed leads (text only).
3. **AI web proof for the company at every effort level.** Today the registry AI proof runs only on Medium and High (see `reserveRegistryProof` in `registryProofGate.ts` and `deepFindRegistry.ts`). Make it run for any UK lead without a `company_number`, including Low, as ONE Gemini grounded search per lead (the internal-AI model split: Gemini for internal checks), inside a per-run AI allowance that is separate from the draft allowance. Auto-pick when the AI-proposed company number is found in the Companies House search results, the name matches by the existing `companyMatchesLead`, the company is active, and location agrees or the lead has no location; conflicts (two plausible active companies, name mismatch) leave the existing choose-a-company prompt. Never auto-pick a dissolved company. Report the cost maths for 100 leads (calls, Gemini cost estimate) and what happens when the Gemini key or allowance is missing (skip with one plain line, never fail the run).
4. **Exceptions list ("Needs a look").** One screen/section listing only leads where a human decision is still needed: T3-only recipients, conflicting company match, suspect website, hard-bounce on the only address. Each row shows the reason and one-click actions (use this address / mark do not email / pick company / dismiss). Nothing else needs review. Reuse the multi-select bulk primitives (`useReviewBatch`, `BulkActionBar`) and the 50-row cap.
5. **Hands-off run (phase 1 = compose what exists).** Investigate the existing selected-leads Autopilot (`run-selected-autopilot`, `docs/RUN-CONTROLS-*`, the picker) and the Deep find queue. Propose and build the smallest wiring so a rep can pick up to 50 leads (or "all not yet researched, newest first") and press one button: Deep find, then auto company pick, then draft, then queue and send to T1/T2 recipients inside the window and daily cap; T3/never leads land in the exceptions list. Reuse Pause/Resume/Stop. If this needs a migration (new run type or columns), write it in the report and STOP before applying; if it can be done without schema change, do that. If the wiring is larger than one item, build the foundations and write the remaining plan.
6. **Sender-reputation guard.** A rolling guard: if bounces are 5% or more of the last 20 or more automatic sends from a mailbox, hands-off sending pauses for that mailbox with a plain message to the rep and an audit line (reuse `autopilot_runs.bounce_count` / `email_outcomes`; no new table unless the report justifies it). Manual single sends are never blocked by the guard. Report the exact thresholds and how a rep resumes.
7. **Report.** Per item: what changed, tests added, gate counts, SQL (not applied), deploy list (functions that import the changed shared files) and anything not verified (live Gemini behaviour, real Companies House matches, send behaviour, browser checks). Include a 100-email-per-day capacity note: how many leads per day the current caps allow end to end (Deep find 50 per run, daily email caps, Hunter/AI allowances) and which cap binds first.

## Hard rules
- Review-before-send is replaced by review-by-exception ONLY for the tiers above and inside existing caps; do not widen to T3 or `never`. The pre-send checker, bounce history, opt-out, blocklist and send window stay in force.
- Do not touch the worker/VPS, allowances in `usage_resources`, the checker identity, or any live data.
- Components under 150 lines; no new dependency; plain-English user text; light and dark themes via existing tokens.
- Gates: `npx tsc --noEmit`, `npx vitest run`, `npm run build`, `git diff --check`, `node scripts/places-edge-typecheck.mjs` with `VITE_SUPABASE_URL=http://127.0.0.1:54321 VITE_SUPABASE_ANON_KEY=local-test-placeholder`.
