Builder: Codex (model `gpt-6.1-sol`), reviewer: Claude, migrations applied by Kevin after review, deploys with Kevin's go-ahead. Parents: `2026-10-14-worker-integration-design.md`, `2026-10-14-jobs-tracker-design.md`, `2026-10-15-background-lookups-design.md`, `docs/LOOKUP-TOOLS-PLAN.md` ("Per-organisation keys and quotas" section).

## Common rules
- Secrets only in Supabase Vault via the existing `app_set_org_api_key` / `app_get_org_api_key` pattern and `resolveOrgApiKey` (`_shared/orgApiKeys.ts`); never returned to the browser, logged, or put in step lines. Settings UI shows only "set / not set" and a masked hint at most.
- Worker calls only through `workerClient` (reserve first, refund at most once and only if no work was done, fail closed). Review-before-send: found data is a proposal/suggestion; nothing is added to sequences automatically. Plain-English text, accessible (labels, focus, contrast), phone width must work.
- New tables/policies need a migration + rolled-back audit script; changes to provider lists need a migration only if a database CHECK constraint lists providers (check `org_api_settings`).

## Part 1 — Desktop pop-ups for the Jobs bar (no database change)
- A browser notification (Notification API) when the tab is in the background (`document.hidden`) and a job (a) newly enters `needs_you`, or (b) newly finishes or fails. Kevin chose both events; NOT for running-progress ticks; no sound.
- Opt-in per person per browser: a "Desktop notifications" card in Settings with a toggle and a plain status ("Off", "On", "Blocked in this browser: allow notifications for this site in the browser settings"). The browser permission prompt is requested only when the user turns the toggle on (a click), never on page load. Preference stored in `localStorage` (wrapped in try/catch; works without it).
- Reuse the existing "seen" logic (`src/lib/jobs/seen.ts`, `notifyLines`, `tabTitleCount`) so a job already shown/seen is not notified again and the first load after sign-in does NOT fire pop-ups for existing jobs.
- Text: title = plain sentence ("Needs you: Fill in details: Creative Works London" / "Finished: Love Living"), body one short line (the job's `detail`). Use the job id + state as the notification `tag` so repeats replace each other. Clicking focuses the tab and navigates to the job's `href`.
- Pure, tested decision function (new file in `src/lib/jobs/`, for example `popups.ts`): input previous items, next items, seen state, hidden flag, enabled flag, permission state; output the list of notifications to show (at most 3 per refresh, then one "+N more" notification). Thin hook mounted in `JobsProvider`/`AppShell`; unmount-safe; no notifications when focus mode is on? (decision: still allowed; focus mode only hides the in-app bar).
- Tests: unit tests for the decision function (first load silent, new needs-you, new finished, failed, already seen, cap of 3, disabled, permission denied, visible tab silent).

## Part 2 — Per-organisation worker address and secret
- New provider `lookup_worker` in `_shared/orgApiKeys.ts` (and the provider lists in `org-api-settings` and the Settings UI), stored as ONE Vault value `https://host|secret` (same idea as the `cro` provider's `email:key`), parsed by a pure, tested function that returns `WorkerConfig | null` (reuse `readWorkerConfig` rules: https only, trimmed origin).
- Resolution order for worker config in `deepFind.ts` and `_shared/lookupJobs.ts` (replace the direct `Deno.env.get('WORKER_URL'/'WORKER_SECRET')`): (1) the organisation's own `lookup_worker` key if set; (2) otherwise, ONLY if the organisation has the existing global-fallback flag (`use_global_api_fallback`), the global `WORKER_URL`/`WORKER_SECRET` function secrets (this keeps Kevin's four organisations exactly as today); (3) otherwise "not set up". Put the resolver in one shared module with unit tests; no behaviour change for organisations without their own key.
- `org-api-settings` edge function: on save, validate the worker address (https, public host: reuse `hostGuard.ts`/SSRF rules; reject private/loopback/link-local), then call `GET <url>/health` with the `x-worker-secret` header with a short timeout; save only if it answers OK; never echo the secret; admins of THAT organisation only (existing admin checks).
- Settings UI card for organisation admins: "Lookup worker": states "Using the shared worker" (flag on, no own key), "Using your own worker" (own key set, shows host only), "Not set up"; fields address + secret (secret input never re-displayed), Save / Remove; plain error lines.
- Usage limits stay per organisation exactly as now (`usage_reserve`). Known limitation to record, not solve: calls to an organisation's own worker still count against the shared worker-wide pool; note it in the handoff as a deferred item.
- Audit/security: rolled-back SQL audit only if a migration is needed; otherwise tests plus a written security checklist in HANDOFF.md.

## Part 3 — Firecrawl (bring-your-own key per organisation)
- New provider `firecrawl`, per-organisation key, NO global fallback (like `hunter`/`apollo`): no key means the step is skipped with the plain line "Firecrawl is not set up for this organisation." Add to the provider lists, `org-api-settings` (validate on save with a read-only Firecrawl account/credit-usage call using the key; never echo it), and a Settings card for admins (same pattern as Hunter/Apollo).
- Use (Kevin chose "step in Deep find and Fill details"): when, after our own page read and the browser scraper, the lead still has no named people with roles (Deep find) or no `owner_name` (enrich job), and a Firecrawl key exists, read ONE team/about page for the lead's confirmed domain through Firecrawl (`POST https://api.firecrawl.dev` scrape endpoint, markdown/html as the existing extractors need), choose the page from links already seen on the site (paths like `/team`, `/about`, `/people`, `/our-team`, `/leadership`) else the home page; extract names and roles with the existing extractors (`extractTeamMembers` / site-people code) and treat results exactly like other site-found people: Deep find shows them under "named on site" (not stored as contacts), the enrich job proposes `owner_name` (and own-domain emails) for review. Caps: 1 Firecrawl page per lead per run; a per-organisation daily cap using `checkRateLimit` (default 100 pages per day, adjustable later); a time reserve like the browser scrape (never starts if it would starve later steps; reuse the `scrapeTimeoutFor` idea with its own constants); hard timeout; failures become plain lines via the existing problem-lines mechanism (new step label `firecrawl`), never raw provider text.
- SSRF/safety: only domains already confirmed for the lead; never follow user-supplied URLs; response size capped; output treated as untrusted (re-validate emails against the confirmed domain; cap counts).
- Cost accounting: record Firecrawl pages used in the Deep find "credits" line (new `firecrawl` counter) without breaking the existing credit-line tests.
- Tests: pure rules module (page choice, caps, parsing, labels) in `_shared/`, tested from `src/lib/`.

## Out of scope
Changing usage-pool accounting for own workers, a global Firecrawl key, automatic sequence enrolment, mobile push, email notifications, Autopilot behaviour.
