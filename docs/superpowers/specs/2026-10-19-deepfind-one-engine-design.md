# Deep find as the one engine — Design

Date: 2026-10-19. Author: Claude (architect). Trigger: Kevin tested Deep find live in front of the UX Tree founder (it worked: owner, email, phone) and flagged: (1) no LinkedIn found; (2) clicking the lead's website opened an unfinished Dreamlabs screen, and the confirmed company website was not applied; (3) the Scraper makes you pick Google Places OR Companies House; (4) three find options (Fill missing details, Find decision maker, Deep find) feel weaker than one strong one: "the custom backend's scraping and email verifying is not used to its full potential".

## Decisions from Kevin (2026-10-19; do not re-ask)
1. LinkedIn: search automatically for relevant stakeholders (owner-like roles: owner, founder, co-founder, CEO, managing director, proprietor, principal; same `isOwnerRole`).
2. Website: when Deep find confirms the company's website, update the lead automatically (rules below).
3. Scraper: run Google Places and Companies House together and merge into one list.
4. Priorities: fewer manual steps, better lead quality, speed.
5. Remove the other two buttons: Deep find does everything. Old lookup jobs and their pages stay for past results; nothing new starts from them.
6. Auto-apply policy: high-confidence facts into BLANK fields only, each automatic change listed on the result with an Undo; everything less certain stays a suggestion with Add / Dismiss.
7. Lead quality: simple Ready / Almost / Needs work badge, sortable and filterable; flag likely wrong matches.
8. Smart depth: quick free pass on every lead; slower or costlier steps (AI web search, Firecrawl, Hunter) only for leads still missing a verified email or decision maker; several leads in parallel within worker limits.

## Rules (binding, unchanged)
Review-before-send; nothing enrols anyone in sequences; worker calls only through `workerClient` (reserve/refund/fail closed); Firecrawl BYO key; secrets never logged; plain-English text; accessible; phone width; migration + rolled-back audit ending in `RAISE EXCEPTION` inside one `DO $$`; Claude applies migrations only with Kevin's per-migration permission; Codex never applies migrations or deploys.

## Phase 1 — Quick fixes (no migration)
**1a Website links.** Websites are stored without a scheme (e.g. `ux-tree.com`), so `<a href="ux-tree.com">` becomes a relative link inside our app (`src/components/pipeline/LeadPanelSections.tsx:99` and any other place a lead/contact website is rendered or opened: `AdditionalDetails.tsx`, Kanban/List cards, Deep find results, scraper results, emails). Add one pure helper `websiteHref(value)` (adds `https://` when no scheme, rejects `javascript:`/`data:`/other schemes, trims, returns null for junk) with tests, use it everywhere a website becomes a link, and keep `rel="noreferrer noopener"` and `target="_blank"`. Do not rewrite stored data.
**1b Confirmed website auto-update.** At the end of Deep find, if a domain is confirmed from the company's OWN website (the "its own website names the company" confirmation, not merely "found by web search") and the lead's saved website is blank, unreachable (the existing site-check failed) or on a different domain that was marked suspect, set `leads.website` to the confirmed site's `https://<domain>` and push the old value into `additional_websites` (dedupe). Never when the saved website is a confirmed good domain; never for directory/social domains; never for domains the user marked "Not their domain" (`blocked_domains`). Recorded in the result's auto-change list with Undo (see 3c).
**1c LinkedIn search.** For each person with an owner-like role (and for the lead's `owner_name`), run one web search through the existing grounded-search path (`webSearchForPerson` / Gemini with the org's key) for the person's LinkedIn profile on the company. Accept only a `linkedin.com/in/<slug>` URL where the result's text names the person AND the company (or its domain). High-confidence match: set the contact's blank `linkedin_url` (auto-capture then creates the linkedin_contacts row as today) and list it as an automatic change with Undo; low-confidence: a suggestion with Add / Dismiss showing the evidence. Max 1 search per person per run, counts against the existing AI-call budget, skipped without an AI key (plain line). Never scrape LinkedIn.

## Phase 2 — Scraper merges sources
`src/pages/Scraper.tsx` (radio for google_places / companies_house / cro) and edge functions `scrape-google-places`, `scrape-companies-house`, `scrape-cro`. Replace the radio with checkboxes: Google Places (default on), Companies House (default on, enabled when the search country is GB), Irish CRO (when its key exists and the country is IE). One search runs every ticked, configured source, merges the results into ONE reviewable list with de-duplication (same company number; else same website domain; else same normalised name + postcode/city), shows which source(s) each row came from, and merges fields (website and phone from Places, company number and officers from Companies House). Keep per-source failure isolation (one source failing shows a plain note and the others still return). Tests for the merge/dedupe module (pure). Check the existing `scrape_jobs`/`raw_leads` model; if a migration is truly needed (for example a `sources` column), record the choice and keep it additive.

## Phase 3 — One engine
**3a Parity.** List everything `enrichOneLead` (Fill missing details) and `findAndStoreDecisionMakers` (Find decision maker) do that Deep find does not yet: Google Places website/phone for name-only leads, Companies House owner name as `owner_name`, Hunter/Apollo decision-maker search, site email/phone proposals, Apollo phone. Write the matrix in HANDOFF.md, then move each missing behaviour into Deep find (as free/quick steps where they are free, deep steps where they cost credits).
**3b Remove the other buttons.** Delete "Fill missing details" and "Find decision maker" from the pipeline list toolbar, the lead page, and scraper results; keep a single "Deep find" button. Leave `/jobs/lookup/:id` and its adapter so old results stay viewable; stop creating new lookup jobs from the UI. The edge function `run-lookup-jobs` and its tables stay (no teardown in this spec).
**3c Auto-apply with Undo.** Deep find may apply, into BLANK fields only and never overwriting: a contact email our checker called `valid`; a confirmed own-site website (1b); owner name/title when the registry or the company's own page names the founder/owner; a LinkedIn match (1c). Every automatic change is recorded in the lead's Deep find result as `auto_applied: [{ table, id, field, before, after }]` (jsonb in the existing result; no new table) and shown as a list "Deep find changed these automatically" with an Undo button per item: Undo restores `before` only if the current value still equals `after`, writes through the user session (RLS), and reports "Changed since, left as is" otherwise. Everything less certain stays a suggestion (Add / Dismiss as today). Nothing touches sequences.
**3d Ready / Needs work.** New columns on `leads`: `readiness text check in ('ready','almost','needs_work')` and `readiness_missing text[]` (migration `065_...` plus audit; existing rows null = "Not checked"). Computed at the end of each Deep find run and shown as a badge on the list/card/lead page and in the result ("Almost: no verified email"). Ready = at least one named decision maker (owner-like or any contact with a role) AND a verified email on a contact or the lead AND a confirmed website. Almost = exactly one of those missing (say which). Needs work = two or more missing, or the website/company flagged as a likely wrong match (different company website, foreign phone numbers on a lead with country GB). Sortable and filterable in the pipeline list. Pure rule module with tests.
**3e Smart depth and speed.** Restructure `processDeepFindLead` into a quick phase and a deep phase. Quick (free, no per-credit cost): saved company, registry (Companies House for GB or null), own-website read, browser scraper, domain discovery without AI, email format and common-format guesses with our checker, person lookups that use only free sources. Deep (only if the lead still lacks a verified email OR a named decision maker after quick): AI web search, Firecrawl team page, Hunter, Apollo, LinkedIn search. Run several leads at once in `runDeepFindTick` (default 3, bounded by worker limits: scraper 2 at a time; per-domain checker throttle 5/min stays; usage reserve per call stays) while keeping the wall budget. Report in the result which phase ran and why deep was or was not needed.

## Delivery order
Phase 1 (one small build), Phase 2, then Phase 3 in two builds (3a+3b+3c, then 3d+3e). Each phase: branch, tests, independent review, Kevin's go-ahead per migration, deploy, live check. Roles: see HANDOFF.md (Codex allowance is low; Kevin decides who builds).

## Out of scope
New data providers, LinkedIn scraping, bulk approve UI, automatic sequence enrolment, email sending changes.
