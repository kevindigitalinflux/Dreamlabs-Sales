# Deep find: actionable suggestions and non-UK companies — Design

Date: 2026-10-16. Author: Claude (architect). Kickoff answers from Kevin (2026-10-16): (1) approving a suggestion = "Add to lead" with "Dismiss"; (2) region = a country field on the lead plus a "None of these / not a UK company" button on the company choice; (3) role mailboxes (privacy@, gdpr@, legal@, careers@ ...) are shown at the bottom, labelled. Builder: Codex (`gpt-6.1-sol`), reviewer: Claude, migration applied by Kevin after review. Trigger: Kevin's UX Tree test (Dublin company, website only): Companies House offered five unrelated UK companies with no "none of these"; non-UK phone numbers made the website "suspect" ("This lead has no usable website"); suggestions are plain text with no way to accept or reject them; the scraper offered privacy@ and gdpr@.

## Parent context
`supabase/functions/_shared/deepFind.ts` (suggestions are collected as `{name, field, value, label}`, stored in `deep_find_leads.domains.suggestions`; named people to check in `named_by_web` / `named_on_site`); UI `src/components/deepfind/DeepFindLeadResult.tsx` (suggestions printed as a text list, no actions); `src/components/pipeline/LookupSuggestions.tsx` (older flow with Add/Dismiss, reuse its behaviour where possible); company choice UI and `resolveRegistry` (`_shared/deepFindRegistry.ts`, `registrySearch.ts`, Companies House); website suspicion (`websiteSuspicion` in `_shared/domainDiscovery.ts`: includes "phone numbers on the website are not UK numbers"); `leads.additional_emails` etc.; `decision_maker_candidates` (contacts with `include_in_sequences`, default off for found people); Irish register helper `_shared/cro.ts` (key pending; do not depend on it).

## Rules (binding)
Review-before-send: nothing is added to sequences automatically; adding a suggestion never enrols anyone. Worker/Firecrawl rules unchanged. Plain-English text, accessible (labels, focus, contrast), phone width OK. Migration + rolled-back audit script; Kevin applies. Never log secrets or provider text.

## Part A — Actionable suggestions (front end + small edge/db support)
- In the Deep find result for each lead, every suggestion row gets two buttons: **Add to lead** and **Dismiss**.
  - A suggestion tied to a named person (the `name` is a person, for example "David Sipple: david@..."): Add = if that person is already a contact on the lead with no email, set the email (only fill blanks, same rule as `fillBlanks`); if no matching contact exists, create a contact (`decision_maker_candidates`) with that email and `include_in_sequences = false`.
  - A company address (name "Company contact"): Add = append to `leads.additional_emails` (deduplicated, case-insensitive; if the lead has no primary email, set the primary email instead). Phones are not suggested as actionable (unchanged).
  - A "named on the web / on site, to check" person (name + role, no address): Add = create a contact with name and role, no email, `include_in_sequences = false`; Dismiss hides it.
- Dismiss is remembered per lead: new column `leads.dismissed_suggestions text[] not null default '{}'` holding normalised keys (`email:<lowercased address>` or `person:<lowercased full name>`). Deep find results and re-runs filter out dismissed keys and anything already present on the lead (primary or additional email, existing contact). Optimistic UI, plain error line on failure, buttons disabled while saving, focus stays sensible.
- Role mailboxes (local part in a pure, tested set: privacy, gdpr, dpo, legal, compliance, careers, jobs, recruitment, press, media, abuse, postmaster, webmaster, noreply, no-reply, donotreply, unsubscribe) are listed at the BOTTOM with the label "Role mailbox, not useful for outreach". Add and Dismiss still work. Useful general mailboxes (hello, info, contact, enquiries, sales, office, admin, team, support) stay in the main list.
- All writes go through the user's own session so RLS applies (same as the lead page); no new edge function unless an RLS gap is found (then stop and record the question).
- Pure helpers (import-free, tested): suggestion key normalisation, role-mailbox classification and ordering, "already on lead" filtering, the add-action planner (which update/insert to perform).

## Part B — Country on the lead and "None of these"
- New column `leads.country text null check (country in ('GB','IE','US','OTHER'))`; null means "not set" and behaves exactly like today (UK assumed) so existing leads are unchanged. Migration `064_lead_country_and_dismissed_suggestions.sql` (check the highest existing number first; this part and Part A's column in ONE migration, with grants/RLS unchanged because the table already has RLS; verify existing UPDATE policies cover the new columns) + a rolled-back audit script `supabase/audits/lead_country_dismissed.sql`.
- Lead detail page: a "Country" select (Not set, United Kingdom, Ireland, United States, Other) next to the website field; saved like other lead fields. The pipeline list/CSV import unchanged except that imported leads keep null.
- Company choice panel (the "Which company is this?" list): add a button **"None of these / not a UK company"**. It opens a small select (Ireland, United States, Other country, "It is a UK company, my company is not listed"). For the first three: set `leads.country` accordingly, clear any candidate list for that lead, and show "Companies House skipped: this is not a UK company." For the last: keep country as is, record that the candidates were rejected so Deep find stops asking for that lead (store the rejection in an existing jsonb or add a tiny column if none fits; record the choice in HANDOFF.md).
- Deep find behaviour when `country` is set and not `GB`: skip Companies House (`resolveRegistry` returns "skipped, not a UK company" with a step line and no candidate list); the website-suspicion rule "phone numbers are not UK numbers" must not fire (accept the dialling prefix of the lead's country: IE +353/08x, US +1; for OTHER, skip that check); Irish CRO and US registers are NOT built here (record "CRO lookup when its key arrives" as a note in the step line only if a CRO key already exists; otherwise nothing).
- When `country` is null the existing behaviour is untouched (regression tests).
- Deep find summary text: replace "This lead has no usable website." when the only issue was the non-UK phone check, and make sure the confirmed website domain is used normally for Ireland.

## Out of scope
Irish CRO / US state register lookups, automatic country detection, changing the usage or worker rules, bulk "apply all suggestions", Autopilot changes.
